# 前端计划：Discord Bot（阶段 1）

> 对应需求：`docs/REQUIREMENTS.md` 第 5.4 / 5.5 / 5.6 节。本文档回答"在 Discord 上怎么做"。
> 状态：草稿，随需求讨论更新。

## 1. 前提与边界

- 阶段 1 只用 Discord **原生组件**：斜杠命令、附件、消息、嵌入（embed）、按钮、下拉菜单（select）、弹窗（modal）、图片 / 文件附件。
- 不做 Discord Activity（内嵌网页），不做外链网页。
- 由此不做：同步播放、拖拽编辑、波形 / 频谱、语音频道播放。

## 2. 安装方式

| 方式 | 说明 | 决定 |
|---|---|---|
| 服务器安装（Guild Install） | 管理员把 Bot 加进服务器，成员在频道里用 | 支持 |
| 用户级安装（User Install） | 用户把 Bot 装到自己账号下，在私信或任何服务器里用，无需管理员 | 支持 |

两种安装共用同一套命令；用户级安装时谱子消息发在私信或当前频道（受该频道权限约束）。

## 3. Discord 硬约束与应对

| 约束 | 数值 | 应对 |
|---|---|---|
| 附件大小 | 免费用户每个附件约 10 MB（Discord 改过几次，以当前官方文档为准；服务器加成后更高） | 实际输入格式限于 mp3 / m4a / ogg / opus；4 分钟 128 kbps mp3 约 4 MB。wav / flac 超限时给出明确提示（"请转成 mp3"） |
| 交互必须 3 秒内应答 | | 立即 defer，回"已收到，排队中 / 处理中，预计 N 分钟" |
| 交互令牌有效期 | 15 分钟 | 单曲全流程目标 < 5 分钟；超过 15 分钟时改用普通频道消息 / 私信发送结果（需要发消息权限） |
| 下拉菜单 | 每个最多 25 项 | 指法调 ≤ 12 项；节奏型控制在 25 以内，超出则先选分类再选节奏型 |
| 弹窗 | 最多 5 个文本框，每框 4000 字 | 粘贴歌词、改和弦够用 |
| 按钮 | 每条消息最多 25 个（5 行 × 5） | 够 |
| 消息长度 | 2000 字 / 嵌入 6000 字 | 嵌入只放摘要信息，足够 |
| 消息编辑频率 | 有限流 | 每次用户操作只编辑一次消息 |
| Bot 回传附件 | 同样受上限 | PNG / PDF / MusicXML 均很小 |

## 4. 命令

| 命令 | 参数 | 行为 |
|---|---|---|
| `/transcribe` | `audio`(附件, 必填)、`title`、`artist`、`lyrics`(可选文本) | 校验 → 入队 → 回执（队列位置、预计时间）→ 完成后发"谱子消息" |
| `/status` | | 列出自己排队中 / 处理中的任务 |
| `/delete` | | 删除自己在服务端的全部数据 |
| `/help` | | 用法、限制、配额 |

也支持：对一条带音频附件的消息使用"消息右键 → 应用 → Transcribe"（Message Command），省去重新上传。

命令名与所有文案提供中 / 英两套，按用户的 Discord 语言设置选择；命令本身通过 Discord 的本地化字段注册。

## 5. 谱子消息（核心界面）

一条消息，由 Bot 发送并在之后每次调整时**编辑这同一条消息**（不刷屏）。

### 5.1 内容

- 附件：谱子第一页 PNG（预览）；多页时附完整 PDF。
- 嵌入：歌名 / 艺术家、"原调 G · 演唱调 F · E 调指法 夹 1 品"、BPM、拍号、低置信和弦数量提示（"有 4 个和弦可能不准，已在谱上标出；需要精修请导出 MusicXML"）。

### 5.2 控件（已定：只做不需要乐理的）

设计原则：面向没有乐理基础的爱好者。全部是下拉和按钮，外加一个粘贴歌词的弹窗；不出现小节号、和弦名、音符时值这类需要懂谱才能填的输入。精修走"导出 MusicXML → 专业软件"。

| 控件 | 类型 | 行为 |
|---|---|---|
| 演唱调 | 下拉 | 以原调为中心列出 −6 … +6 半音，每项显示"F（降 2）"；选后重算指法调选项并重渲染。默认保持当前指法调不变、只动变调夹；若变调夹会变成负数，则自动切到品数最小的可用指法调并在嵌入里说明 |
| 指法调 | 下拉 | 在当前演唱调下，每项显示"X 调指法（夹 N 品）"，按品数升序；> 7 品的排后并加"不推荐"；负品数的不列出。系统默认选品数最小的；选后重渲染 |
| 节奏型 | 下拉 | 含"无"；选后重渲染。**[建议]** 选项文字附一句口诀式描述（"下 下上 上下上"），弥补看不到图 |
| 简化和弦 | 按钮（开 / 关，显示当前状态） | 切换后重渲染；默认开（已定） |
| 歌词 | 按钮 → 弹窗 | 见第 6 节 |
| 导出 | 下拉 | PDF / PNG 全页 / MusicXML；选后以附件回复 |
| 重置 | 按钮（P1） | 回到系统初始结果（原调、默认指法调、默认节奏型、识别出的歌词） |

共 7 个控件，一条消息放得下，不需要分页或二级面板。所有调整都是无状态参数（演唱调、指法调、节奏型、简化、歌词文本），不需要版本历史。

### 5.3 权限

- **已定：只有发起任务的人能操作控件**（服务器频道、私信、用户级安装一视同仁）。其他人点击时得到仅自己可见的提示："这张谱由 @X 发起；你可以用 `/transcribe` 生成自己的一份。"
- 实现：发起者的用户 ID 存在项目记录里，每次控件交互先比对。

## 6. 弹窗设计

只有一个弹窗：**歌词**。一个多行文本框，预填当前歌词全文（按行）。用户粘贴 / 修改后提交，系统重新对齐、重渲染。超过 4000 字时自动拆到最多 5 个文本框。

不做的弹窗（已移出阶段 1）：改和弦、换指法、变调夹覆盖、速度 / 拍号、改简谱。

## 7. 任务生命周期与文案

```
/transcribe
  ├─ 校验失败 → 仅自己可见的错误：格式不支持 / 超过 10 MB / 超过 8 分钟 / 今日配额已用完
  ├─ 入队 → 回执："已收到《xxx》，前面还有 N 首，预计 M 分钟。完成后会在这里通知你。"
  ├─ 处理中 → （可选）每个大环节更新一次回执："正在分轨… / 识别和弦… / 对齐歌词… / 排版…"
  ├─ 成功 → 发谱子消息，并 @发起者
  └─ 失败 → "处理失败：<原因>"，原因枚举：超时 / 未检测到人声（歌词与简谱为空，但和弦谱照出）/ 音频损坏 / 服务异常（附任务 ID 便于反馈）
```

超过 15 分钟（交互令牌过期）时，结果改为普通频道消息发送；若 Bot 在该频道没有发消息权限，则私信发起者。

## 8. 与后端的接口（前端需要什么）

| 接口 | 输入 | 输出 |
|---|---|---|
| 提交任务 | 音频文件、歌名、艺术家、歌词（可选）、用户 ID、来源（guild / DM）、语言 | 任务 ID、队列位置、预计时间 |
| 任务状态 | 任务 ID | 排队 / 处理中（当前环节）/ 成功 / 失败（原因） |
| 获取项目 | 项目 ID | 结构化结果 + 当前调整参数 |
| 渲染 | 项目 ID、调整参数（演唱调偏移、指法调、节奏型、简化开关） | PNG 第一页、PDF |
| 重新对齐歌词 | 项目 ID、歌词文本 | 更新后的 `LyricSyllable` + 渲染结果（≤ 30 秒） |
| 重置 | 项目 ID | 初始参数 + 渲染结果 |
| 导出 | 项目 ID、格式、当前调整参数 | 文件 |
| 删除用户数据 | 用户 ID | 确认 |
| 配额查询 | 用户 ID、guild ID | 剩余次数 |

渲染接口必须秒级返回（不触发模型推理）；重新对齐歌词只跑对齐模型，不重跑分轨与识别。

## 9. 技术选型 **[待定]**

| 项 | 候选 | 倾向 |
|---|---|---|
| Bot 框架 | discord.py（Python，与核心库同语言）/ discord.js（Node） | **[建议]** discord.py，减少语言栈 |
| 网关模式 | Gateway（长连接）/ HTTP Interactions Endpoint（无状态 webhook） | **[建议]** Gateway 起步简单；后续可切 HTTP 以便水平扩展 |
| 消息状态 | 项目 ID 编码进控件 `custom_id`，当前调整参数存服务端；Bot 重启不丢状态 | 已定 |

## 10. 开放问题

1. 节奏型库的分类方式（按拍号？按风格？）决定下拉是一级还是两级；以及选项里怎么用文字描述节奏型。
2. 是否在处理中逐环节更新回执（多几次消息编辑 vs 更好的等待体验）。
3. 公共实例的 Bot 名称、头像、`/help` 里的服务条款文案。
