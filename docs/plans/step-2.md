# 第 2 步实现计划：和弦 + 调性

> 对应：`docs/ROADMAP.md` 第 2 步；需求 `docs/REQUIREMENTS.md` 5.2（`Chord`、`Key`）、7（可测试性、许可证）、9（和弦准确率）。
> 状态：**已完成**（2026-11-07）。验收数字见第 12 节与 `docs/benchmarks/step-2-chords.md`；决定记录见第 8 节（1–18）。

## 1. 目标与范围

在第 1 步的拍网格之上接入和弦与调性识别。做完后 `opencapo analyze` 输出：

1. `Chord` 序列：12 根音 × 14 种性质（第 0 步定的 `ChordQuality` 枚举）+ 转位（`bass`）+ 置信度；每个和弦的起止都落在拍上；和声稀薄的段落留空（不填占位和弦）。
2. `Key`：调（主音 + 大 / 小）+ 置信度。
3. 选型对比页：各候选专家单独与组合后的准确率与耗时，由负责人据此拍板最终组合。
4. 评测脚本与结果文件（`docs/benchmarks/step-2-*.md`）。
5. 新引入的权重许可证写进 `docs/plans/backend.md` 2.1 节。

**本步不做**：训练或微调任何模型；简化和弦显示（第 3 步的编配规则）；节奏型；人声旋律；段落结构。

## 2. 方法：多专家 + 规则融合，在拍网格上决策（决定 1，已定）

模仿人类扒谱的流程——先定框架（拍、调），抓低音，定性质，在拍上换，再验证。深度学习模型只负责"听"，决策用规则。

```
                 ┌─ E1  大词表 DL 模型（BTC）              ──┐
混音 ────────────┼─ E2  结构化 DL 模型（crema / lv-chordia） ─┤ 每拍的和弦后验分布（映射到同一词表）
                 └─ E3  色度模板匹配（规则，自己实现）     ──┤
bass 分轨 ───────── E4  低音音高检测（规则）               ──┤ 每拍的低音音级
混音 + 和弦统计 ──── E5  调性估计（Krumhansl 模板 + 和弦统计互校）┘ 调性先验

                       融合层（第 1 步的拍网格上）
            ① 各专家的逐帧输出按拍区间聚合（后验取平均）
            ② 加权融合（权重少，在开放数据的一半上调，另一半报数）
            ③ 调性先验：调内和弦加分，调外罕见和弦减分
            ④ 低音约束：低音 ≠ 根音但属于和弦音 → 转位；与所有候选都矛盾 → 降置信度
            ⑤ Viterbi 平滑：强拍换和弦便宜，小节中间换贵，最短一拍
            ⑥ 和声稀薄：各专家对 N（无和弦）的支持占优 → 留空
            ⑦ 置信度 = 融合后最优标签的后验 × DL 专家对根音的一致度

                       Chord（root, quality, bass, confidence）+ Key
```

### 2.1 各专家

| 专家 | 类型 | 输入 | 产出 | 作用 |
|---|---|---|---|---|
| E1 BTC（Park 等，ISMIR 2019） | DL，170 类：14 性质 × 12 根音 + N + X | 混音 | 逐帧后验 | 性质词表与我们的枚举几乎一致（它有 minmaj7，没有 `5`）；大词表主力 |
| E2 lv-chordia（Jiang 等，ISMIR 2019 的 pip 封装；crema 因环境淘汰，见决定 3） | DL，五网络集成，结构化输出：根音 / 三和弦、低音、七音、扩展音 | 混音 | 逐帧后验（经其解码器按我们的 14 种性质组合） | 架构与 E1 不同、错法不同，投票才有价值；词表缺 `5`，由 E3 补 |
| E3 色度模板 | 规则：CQT 色度 → 14 × 12 个和弦模板的余弦打分；自己实现（不用 GPL 的 Chordino） | 去鼓混音（bass + other + vocals） | 逐帧打分 | 不依赖任何训练集；弱但独立；也是 `5`（强力和弦）唯一的来源 |
| E4 低音检测 | 规则：bass 分轨上做基频跟踪（pYIN 或低频 CQT 峰值），按拍投票 | bass 分轨 | 每拍低音音级 + 强度 | 人类"先听贝斯"；转位只能从这里来 |
| E5 调性 | 规则：Krumhansl–Schmuckler 模板在整曲色度上打分；再用和弦序列（按时长加权的根音 / 性质直方图）独立估一次；两者互校 | 混音；E1–E3 的输出 | 调 + 置信度 | 不用 AGPL 的 essentia、CC-NC 的 madmom；不一致时降置信度 |

DL 专家是可替换插件（`ChordExpert` 协议），规则专家与融合层是纯代码，CPU 单元测试覆盖。

### 2.2 词表映射

所有专家的输出先映射到我们的词表（`ChordQuality` 14 种 × 12 根音 + N）。映射规则写成一张表并有测试：例如 BTC 的 `minmaj7` → 最近的 `min`（降置信度）；crema 的音级集合按模板最近匹配；超出词表的一律降级到最近的三和弦并降置信度，而不是丢弃。

### 2.3 融合层的可调参数

专家权重（3 个）、调性先验强度（1 个）、换和弦代价（强拍 / 非强拍各 1 个）、N 的阈值（1 个）。参数少，在评测集按演奏者 / 曲目分半的一半上网格搜索，另一半报数，并把两半的数字都写进结果，防止把测试集调进参数。

### 2.4 置信度定义

每拍：`confidence = p_fused(best) × agreement`，其中 `p_fused` 是融合后最优标签的归一化后验，`agreement` 是 DL 专家中根音与最优标签一致的比例（只有一个 DL 专家时为 1）。同一和弦跨多拍时取各拍的最小值。低于阈值（默认 0.5，`Analysis` 之外的配置项）的和弦在谱上标出。定义写进代码注释与本文档。

### 2.5 转位

E4 的低音音级 `b` 与融合结果 `root:quality` 的关系：`b == root` → 原位；`b` 是该和弦的三音 / 五音 / 七音 → `bass = b`；其它 → 不记转位、置信度乘 0.7。E2 自带的低音估计只作 E4 的旁证（两者一致时加分）。

### 2.6 强力和弦 `5`

没有 DL 模型输出它。规则：E3 的色度里根音与五度强、大三度与小三度都弱于阈值 → 把融合结果改判为 `5`。优先级低，先占位并写测试，阈值在评测集上看效果后定。

### 2.7 调性互校（E5 细则）

两条路各给一个 24 维（12 主音 × 大小）打分向量：色度模板法与和弦统计法。归一化后加权相加取最优（色度权 0.5，它是两条路里更吵的一条）；两条路的最优不同时置信度减半。

首轮评测后改进的两条规则（用 `scripts/eval_key_inputs.py` 在 GuitarSet 调参半的伴奏曲目上选定，报数半与 AAM 单一调性曲目只用来验证）：
- **和弦统计按窗口投票**：16 秒窗、8 秒步，每个窗的 24 维分数归一化后取平均，而不是整曲合并统计。整曲合并会把转调曲（或模型输出漂移的段落）两个调的和弦混成第三个调。
- **关系大小调之争按"票数"判**：最优调与它的关系大小调分数差在 5% 以内时，比较两者主和弦的总时长，再加上开头与结尾和弦的票（是该调主和弦记 2 个平均和弦时长，是该调属和弦记 1 个）。两个调共用同一组音，词袋统计分不开，乐句的起点与落点是人耳区分它们的线索。
- 验证结果（导出文件 `docs/benchmarks/step-2-key-inputs.json.gz`，CPU 复算）：调参半伴奏 0.856 → 0.967；报数半伴奏 0.711 → 0.789；AAM 单一调性 0.847 → 0.931；AAM 全部 0.634 → 0.698。试过但没用的：七和弦按三和弦判音阶归属（蓝调 / 放克的 I7、IV7），调参半持平、验证集无提升，不采用。

## 4. 评测与计时脚本

- `scripts/eval_chords.py`：对每个专家单独、以及融合后，在评测集上算 mir_eval 的 `chord` 指标：`majmin`、`sevenths`、`majmin_inv`、`sevenths_inv`（按时长加权的正确率），另给 `root` 与分段数比；按风格 / 流派分组；每曲耗时。调参集 / 报数集分开报。输出 `docs/benchmarks/step-2-chords.md` / `.json`。
- `scripts/eval_key.py`（或并入上面）：调性正确率，另报 mir_eval `key.weighted_score`（相对调、五度圈相邻调给部分分）。
- `scripts/time_pipeline.py` 扩展：加 `chords`、`key` 两个环节。
- 自检：标注当预测 → 1.0；各专家单独的数字与其论文报告值对照（文献值是 Beatles 上的，只看量级）。

## 8. 负责人决定

### 1. 已定：方法用"多专家 + 规则融合，在拍网格上决策"

- 结构如第 2 节：两个架构不同的 DL 专家 + 三个规则专家（色度模板、低音检测、调性），融合层带调性先验、低音约束、Viterbi 平滑、N 判定与置信度公式。
- 理由：单个 DL 模型没有一个能可靠给出转位，且各自训练集偏窄；人类专家的流程（先调与拍、抓低音、定性质、在拍上换）全部能以规则落地，并且这些规则是纯代码、可测。
- 负责人补充的规则：和声稀薄的段落输出 N（谱上留空），不硬填。
- 对流行歌的鲁棒性：五个专家都只看音高内容，不依赖吉他音色；DL 专家的训练数据本身就是流行 / 摇滚完整混音。方法不走"先转录全部音符再配和弦"的路线：多乐器复调转录比和弦识别难一个量级，且和弦是和声抽象而非音符汇总；只有低音线被真正转录。
- 未采用：单一模型 + 后处理（无法互校、无转位来源）；转录优先路线。

### 2. 已定：评测用 GuitarSet + AAM（抽 500 首），两者都设门槛

- Isophonics Beatles 没有音频，负责人确认只能用开放数据；公开的和弦数据集几乎都不附音频，能用的只有真实但编制单薄的 GuitarSet 和编制完整但合成的 AAM，两者互补。
- 门槛沿用路线图原数字（和弦 majmin ≥ 80%、调性 ≥ 85%），数据集换成这两个，两者都要过。AAM 抽 500 首足够，3000 首全跑要 200 GB 音频。
- GuitarSet 兼作融合参数的调参集（按吉他手分半），AAM 不参与调参。
- 已同步修改：`REQUIREMENTS.md` 第 7 节可测试性、第 9 节和弦与调性两条；`ROADMAP.md` 第 2 步；`step-0.md` 第 8 节的"测试集污染"风险标记为已消解。
- 未采用：只在 GuitarSet 上设门槛、AAM 只报数（可能高估）；只用 AAM（完全没有真实录音）；自建人工标注集（负责人无法提供开放数据以外的数据）。

### 3. 已定：BTC、crema、lv-chordia 三个都进 spike，生产最多留两个

- 候选：BTC（PyTorch；代码 MIT，权重随仓库分发、未单独声明；170 类，无低音）、crema（TensorFlow / Keras；BSD-2；结构化输出根音 / 低音 / 音级集合）、lv-chordia（PyTorch ≥ 2.13；MIT；结构化，170 / 600 类词典）。
- spike 内容：每个专家单独、两两组合 + 规则专家、三个全上，分别在 GuitarSet（调参半 / 报数半）与 AAM 500 首上报 majmin / sevenths / 转位级别准确率与每曲耗时。
- 取舍规则（先写死）：
  1. 生产组合从"BTC + 一个结构化模型"里选；结构化模型二选一时同为 torch 的 lv-chordia 优先，除非 crema 在两个评测集的 majmin 上都高出 3 个百分点以上。
  2. 环境问题（lv-chordia 要求的 torch 版本、crema 的 TensorFlow）可以修，负责人确认服务器环境可调整；升级 torch 时记录新的版本组合到 `docs/benchmarks/README.md`。
  3. 融合后的数字必须高于最好的单个专家，否则先改融合规则，不硬上。
- 排除：accordoai（本科论文级实验，只用 Beatles 训练）；ChordFormer（无公开代码）；madmom 和弦（CC-NC、只有大小三和弦）；autochord（只有大小三和弦）。
- **实施中的结果**：crema 按规则 2 淘汰——它调用 Keras 2 的 `model_from_config`，Keras 3 没有；Keras 2 需要 TensorFlow ≤ 2.15 与 Python ≤ 3.11，与 node28 的 3.12 和本仓库环境都不兼容，等于单独建一套环境，只尝试一次（降级 setuptools）后停止。BTC 与 lv-chordia 在合成的 C–F–G7–Am 上都正确，进入 spike。
- 未采用：只测 torch 系（少一个与低音互校最直接的架构）；只用 BTC（投票失去意义）。

### 4. 已定：GuitarSet 按吉他手分半调参，AAM 只报数

- GuitarSet 吉他手 00–02 的 180 段调参，03–05 的 180 段报数；按人分而不是按段分，因为同一人的伴奏 / 独奏、两种速度版本高度相关。
- AAM 500 首确定性抽样（脚本里固定规则），不参与调参。
- 网格搜索，每参数 3–5 个取值，目标是调参半的 majmin；结果文件里两半并列，验收看报数半与 AAM。

### 5. 已定：调性互校按 2.7 节

色度模板法与和弦统计法各出 24 维打分，归一化相加取最优；两法不一致置信度减半；关系大小调按 I 级与 vi 级总时长判。验收只看主音 + 大小全对；另报 mir_eval 加权分作参考。

### 6. 已定：转位按 2.5 节

低音检测的音级等于根音 → 原位；是三音 / 五音 / 七音 → 记转位；都不是 → 不记转位、置信度乘 0.7。DL 专家的低音估计只作旁证。分析层照实记转位，显示与否由第 3 步的简化开关决定。

### 7. 已定：GuitarSet 的门槛只按伴奏（comp）曲目算，独奏（solo）只报数

- 背景：node28 首轮评测，GuitarSet 报数半 majmin 只有 0.488。拆开看，伴奏曲目 0.776、独奏曲目 0.200（committee 调参后；BTC、lv-chordia 单独也是同样的分裂）。逐拍对照伴奏曲目没有移调、没有大小调反转、没有时间错位，实现无系统性错误。
- 原因：GuitarSet 每条和弦进行录两遍，独奏那遍是单音旋律即兴，录音里没有和声，而"谱面和弦"标注写的是独奏者心里的进行。对没有和声的音频做和弦识别在定义上不成立，任何识别器都过不了。
- 决定：GuitarSet 的两条门槛（majmin ≥ 80%、调性 ≥ 85%）只按报数半的伴奏曲目（90 段）算；独奏曲目在同一张表里报数、标"参考"。报表脚本把 comp / solo 分开列，门槛判定由脚本产出。
- 已同步修改：`REQUIREMENTS.md` 第 9 节两条；`ROADMAP.md` 第 2 步验收两条；本计划第 3 节表与第 11 节。
- 未采用：维持全部曲目算门槛（只能把门槛降到 0.5 以下，数字失去意义）；GuitarSet 不设门槛、只靠 AAM（失去真实录音把关）。
- 代价：GuitarSet 有效样本从 180 段降到 90 段；首轮伴奏 0.776 仍差门槛，调性 0.711 差得更多，后续要在融合与调性估计上补。

### 8. 已定：AAM 的调性门槛只按全曲单一调性的曲目算

- 背景：AAM 500 首里 428 首中途转调（各段标签不同，中位数最长段占比 0.65）。"每首一个调"的任务对这些曲子没有唯一真值；首轮调性错误 183 首里 171 首是转调曲，单一调性的 72 首正确率 0.833（规则改进后 0.931）。
- 决定：AAM 的调性门槛（≥ 85%）只在 `key_share == 1` 的曲目上算（脚本按标注自动划分，人不挑）；转调曲目保留在报表里，报"估计落在任一占时 ≥ 1/3 的调上"的命中率，不设门槛。
- 已同步修改：`REQUIREMENTS.md` 第 9 节调性一条；`ROADMAP.md` 第 2 步验收一条；本计划第 3 节表与第 11 节；报表脚本的"验收"列。
- 未采用：维持 500 首全算（测的是标签歧义）；用放松指标作门槛（会掩盖单一调性曲目上的真错误）。
- 代价：门槛样本只有 72 首，一首曲子约 1.4 个百分点。

### 9. 记录：融合层与规则层的四轮优化（负责人授权自行决定）

首轮报表后，负责人要求先把指标调好再进第 3 步，并把模型设计层面的自由度交给实现方。每轮都在 GuitarSet 调参半上选参数、报数半与 AAM 单一调性曲目只用来验证，由 `scripts/eval_chords.py` 重出报表、`scripts/analyze_chords.py` 重出错误分析（`docs/benchmarks/step-2-error-analysis.md`）。

| 0 | 首轮 | — | 0.776 | 融合 79.0% 帧正确，最好单模型 80.0%，任一模型正确 84.5% |

### 10. 已定：用谱子渲染的合成音频做"曲库"评测，不用任何录音

- 负责人不持有也不会提供歌曲录音（版权风险），但能提供他熟悉的歌的吉他谱（和弦 + 简谱 + 变调夹）。
- 做法：`opencapo.sheet` 把谱子文本解析成小节级的和弦与简谱，用 Karplus–Strong 拨弦合成扫弦吉他、简单贝斯与带颤音的旋律声部渲染成音频，同时导出谱子自带的参考（变调夹换算后的实际和弦、演唱调、拍网格、旋律）。`scripts/eval_chords.py --sheets` 把它当第三个数据集报数，不设门槛。
- 它能测的：整条流水线在负责人曲库上的和弦进行、变调夹与调性换算、拍网格；以及第 4 步（旋律 → 简谱）的现成真值。不能测的：真录音（人声、混音、演奏变化）的难度，分数应视为上限。
- 仓库只放公有领域示例《小星星》（`docs/examples/xiaoxingxing.sheet`）；负责人录入的歌谱与渲染音频留在本地 / node28。

### 13. 已定：负责人曲库先整理、按版式试点，再批量识谱（2026-11-04）

- 背景：负责人一次提供了 238 首歌的谱子图片（约 690 个文件），来自多个网站，版式、分辨率、水印各异；同一首常有两个版本或重复下载，页序只能从文件名或图片内容推断，变调夹有时只写在文件名里。
- 决定：先写确定性的整理脚本（`scripts/sheet_triage.py`）：每首去重、定页序、从文件名提取变调夹、给来源版式打标签、输出"歌名 / 页数 / 版式 / 问题"一张表供负责人过目；然后每种版式挑约 2 首共约 10 首做试点，按版式调切图阈值，复核清单交负责人；最后批量跑其余曲目。

- 已知不可用的版式：只有六线谱与歌词、没有简谱行的谱（如 oguitar 版式），渲染不出旋律，单独标出。

### 15. 已定：识谱按"行"读图，小节由模型分（2026-11-04，负责人授权自行决定）

- 背景：试点 10 首（8 个版式）发现按小节切图的确定性步骤在 5 个版式上失败，方式各异：数字"1"或"0"的竖笔与小节线等高、左侧大括号抬高参考高度、小节线只比数字高一两个像素。三版规则各修好两三个版式又弄坏另外两三个；曲库来源 56 家，长尾无法逐一调参。
- 决定：切图层只负责找行（谱表线是整页最长横线，各版式稳定），整行交给模型，模型输出小节数组；两遍读图、音乐级比对、拍数自检、第三遍裁决机制不变，单位从小节改为行。依据：四个版式各试一行，小节数、和弦、旋律、歌词全部正确。
- 负责人表态："这个都是细节，你自己决定"。识谱内部实现（切图、读图协议、自检）此后由实现方自行决定，只汇报结果。

### 16. 已定：曲库样本集上的调性按"主音"验收，关系大小调算对（2026-11-05）

- 背景：试点 9 首中调性精确匹配 7/9，两处错误（再见杰克、乌兰巴托的夜）都是估计为参考调的关系小调；查看和弦进行，两首本是小调歌（Am–F–E、Fmaj7–G–Am），谱子按中文吉他谱习惯只写 1=F / 1=bE。中文谱的 1=X 只表达所用音级的大调，不记录大小调。
- 负责人决定：曲库样本集上，估计为参考调或其关系小调都算正确（报表列"调性主音"，验收用它）；"调性精确"仍列出作参考；GuitarSet 与 AAM 自带大小调，仍按精确匹配。
- 理由：产品里变调夹品数与指法调只取决于主音所在的那组音，关系大小调给出相同的指法调。
- 备选被否：维持精确匹配（记谱习惯导致的"错误"会压低门槛）；识谱时让模型判大小调写进参考值（多一个无法验证的环节，与产品输出无关）。
- 已同步修改：`REQUIREMENTS.md` 第 9 节、`ROADMAP.md` 第 2 步验收、本计划第 12 节、`scripts/eval_chords.py` 的报表。

### 17. 记录：识谱读出的页眉按和弦形状判断 1= 是演唱调还是指法调（2026-11-07，实现方按决定 15 的授权自行决定）

- 首次全量评测调性主音 0.877，27 首错误中 16 首是参考值错误：页眉只印"1=C，变调夹 2 品"时 C 是和弦形状的调（指法调），识谱把它当成了演唱调，参考调偏低一个变调夹，旋律也被渲染低了；估计器听到的正是实际发声的调。
- 处理：读完和弦后求和弦形状所属的大调（`omr.shape_key`，按顺阶和弦时长投票）；它等于页眉的 1= 且有变调夹、页眉又没另印选调时，1= 视为指法调，演唱调 = 1= + 变调夹（`omr.reconcile_header`）。规则是确定性的，有单元测试，不看评测结果逐首改参考值。
- 结果：调性主音 0.877 → 0.936，精确 0.636 → 0.686；和弦分数不变（和弦参考本来就按变调夹换算，不受影响）。

## 10. 样本生成器（第 2 步的独立模块）

> 负责人确认（决定 10 及后续讨论）：把"谱子 → (合成音频, 真实标注)"做成第 2 步里一个独立模块；识谱前半段允许用 agent 的读图能力做识别与纠错。

### 10.1 目的与边界

- 目的：不用任何录音，从负责人曲库的吉他谱生成带标注的评测样本，供第 2 步（和弦、调性、拍点）与第 4 步（旋律 → 简谱）使用。
- 输入：PDF 或图片（PNG / JPG / WebP，一页一图或多图），都先栅格化成统一分辨率的页图再识谱。
- 不是产品功能：不进 Discord 流水线，不对用户开放；代码放在核心库 `opencapo.sheet` 下是因为谱子文本的解析器以后第 3、4 步输出简谱时要复用，渲染器与识谱器只服务评测。
- 这个样本集就是第 2 步验收的依据（决定 11）；GuitarSet 与 AAM 降为公开数据集参考。合成音频的分数是真录音的上限，这一点在报表里注明。

### 10.2 流水线

```
PDF 谱子 ──识谱（OMR）──▶ 谱子文本（.sheet）──渲染──▶ 样本（.wav + .json）──▶ 评测 / 第 4 步
              ▲   │
              └───┘ 自检不通过的小节回到识谱重读
```

1. **识谱**（`scripts/sheet_ocr.py read`，已做）：
   - 确定性部分：PDF 或页图目录按 300 dpi 栅格化；按行投影找到每一行（和弦图条 + 六线谱 + 简谱 + 歌词），把每一行整行切成一张图，生成一份"工作单"（JSON：页、行序号、行图路径）。**不找小节线**（决定 15）：小节线在不同版式里与数字"1"或"0"一样高，规则无法稳定区分，由读图模型按小节线自行分段。
   - 读图部分：由 Claude Code 的无头模式（`claude -p`，走负责人自己的登录，不用 API key）逐行读放大一倍的行图，输出该行的小节数组（每小节：和弦、简谱、歌词；简谱含下划线时值、上下八度点、附点、连音线）。低八度点贴着下划线、附点、跨小节连音线是已知易错点，读图提示里显式列出。**每一行独立读两遍**（分批边界错开），逐小节按解析后的音乐内容比对；单遍读图快但会漏八度点和十六分分组，这类错自检看不出来（拍数照样凑满），两遍比对能抓到。
   - 自检（确定性）：每小节顶层拍项数必须等于拍号；和弦名必须可解析；跨小节连音线两端音高必须一致；同和弦的重复段落（八小节）旋律应基本一致，个别不同的小节标出。两遍不一致或含自检不过小节的行，用放大两倍的行图单独读第三遍裁决；三遍都不一致的行，其全部小节进"待复核清单"。
   - 装配：头部（标题、`1=`、变调夹、速度、拍号）+ 各小节 → `.sheet` 文本。
2. **渲染**（`opencapo.sheet.render`，已做）：扫弦吉他（拨弦物理模型）/ 钢琴柱式和弦 + 贝斯 + 钢琴旋律；导出参考：变调夹换算后的实际和弦（起止秒、Harte 标签）、演唱调、拍点与强拍、旋律（起止秒、MIDI 音高）。
3. **样本集格式**：一个目录一套，`manifest.json` 记录格式版本、生成时间、代码版本（git 提交号）、渲染参数（音色、贝斯、旋律），每首的文件名、头部信息（标题、调、变调夹、速度、拍号）、小节数、时长、来源（识谱 / 人工录入）与待复核小节数；每首三件：`<name>.sheet`、`<name>.wav`、`<name>.json`。清单由 `scripts/sheet_ocr.py manifest DIR` 扫目录重建（`read --render` 与 `sheet_synth.py` 结束时自动重建），评测只认清单（决定 12）。负责人的曲库样本集留在本地 / node28，不进仓库；仓库只放公有领域示例《小星星》。
