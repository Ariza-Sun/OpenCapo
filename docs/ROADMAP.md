# OpenCapo 阶段 1 路线图

> 给项目负责人看的分步清单。每一步由负责人确认后交给 agent 执行；完成的标准写在"验收"里，没达到就不算完成。
> 顺序原则：**最不确定的先做**。阶段 1 的风险全在分析质量（和弦准确率、歌词对齐、人声切音符），Discord 只是最后一层薄壳，放最后。
> 对应需求：`docs/REQUIREMENTS.md`；实现方案：`docs/plans/`。

## 总览

| 步 | 名称 | 里程碑 | 主要风险 |
|---|---|---|---|
| 0 | 项目骨架与数据模型 | — | 低 |
| 1 | 分轨 + 节拍 + BPM | M1 | 中：节拍准确率 |
| 2 | 和弦 + 调性 | M1 | **高**：和弦模型选型与准确率 |
| 3 | 编配引擎 | M1 | 低：规则明确 |
| 4 | 渲染与导出（三层谱） | M1 | 中：简谱 / 六线谱自绘工作量 |
| 5 | 歌词：粘贴对齐 + 识别 | M1 | **高**：中文对齐效果 |
| 6 | Discord Bot | M1 | 低：工程为主 |
| 7 | 人声旋律 → 简谱行 | M2 | **高**：切音符与量化 |
| 8 | 公共实例上线 | — | 中：运维、成本 |

每一步的产出都要进 main，并且 CI 绿。

---

## 第 0 步：项目骨架与数据模型

**做什么**
- Python 包 `opencapo`，`pyproject.toml`，格式化 / lint / 测试工具链，GitHub Actions CI。
- 数据模型：`Beat`、`Tempo`、`Key`、`Chord`、`Note`、`LyricSyllable` 及顶层 `Analysis` 对象（见需求 5.2），JSON 序列化 / 反序列化。
- 调整参数对象 `Arrangement`：演唱调偏移、指法调、节奏型、简化开关、歌词文本。
- 一条空的 CLI：`opencapo analyze <audio> --out <json>`，先跑通参数解析与输出。

**验收**
- `pip install -e .` 成功；`pytest` 通过；CI 在 PR 上自动跑并通过。
- 数据模型有单元测试，JSON 往返无损。
- 一首示例音频跑 `opencapo analyze` 能输出合法（可为空）的 JSON。

---

## 第 1 步：分轨 + 节拍 + BPM

**做什么**
- 接入分轨模型（Demucs 或 BS-RoFormer），输出 vocals / drums / bass / other，只在流水线内部使用。
- 接入节拍 / 强拍模型（all-in-one、Beat This!、madmom 三选一，由实测决定），输出 `Beat`（小节 + 拍）与全局 BPM。
- 评测脚本：在 GTZAN-Rhythm（或 Ballroom）上算节拍 F-measure。
- 记录每个环节耗时。

**验收**
- 节拍 F-measure ≥ 85%（评测脚本输出，数字进 README 或 docs）。
- 4 分钟歌曲在一张 GPU 上：分轨 + 节拍 ≤ 90 秒。
- `opencapo analyze` 输出含 `Beat`、`Tempo`；分轨文件在流程结束后不残留。
- 模型权重许可证逐个列在 `docs/plans/backend.md`。

---

## 第 2 步：和弦 + 调性

**做什么**
- 方法按 `docs/plans/step-2.md`：多个开源和弦模型 + 规则专家（色度模板、低音检测、调性）在拍网格上融合。先做选型 spike：各候选专家单独与融合后在 GuitarSet、AAM 上跑出准确率与速度，写成一页对比，由负责人拍板最终组合。
- 输出 `Chord`：12 根音 × ≥ 14 种性质 + 转位 + 置信度。
- 和弦边界对齐到第 1 步的拍网格。
- 调性：和弦统计规则法 + 一个音频调性模型互校，输出 `Key`。

**验收**
- GuitarSet 与 AAM（抽 500 首）上 major/minor 级别准确率均 ≥ 80%；七和弦 / 转位级别的数字也要给出（作为基线，不设门槛）。Isophonics Beatles 不提供音频，不用。
- 输出的每个和弦都落在拍上，没有不对齐网格的边界。
- 置信度有定义（写在代码注释和文档里），低置信阈值可配置。
- 调性在 GuitarSet 与 AAM（同一批 500 首）上正确率均 ≥ 85%。
- 4 分钟歌曲：和弦 + 调性 ≤ 30 秒。

---

## 第 3 步：编配引擎

**做什么**
- 演唱调 / 指法调 / 变调夹换算：`capo = 演唱调 − 指法调`，候选指法调列表与排序规则（需求 5.3）。
- 指法库（JSON）：每个和弦至少一种按法，含难度；默认选法规则。
- 节奏型库（JSON）：≥ 10 种，覆盖 4/4、3/4、6/8，每种带口诀式文字描述与推荐 BPM 区间；默认推荐规则。
- 简化和弦映射规则。
- 页眉信息生成：原调、演唱调、指法调、变调夹、BPM、拍号。

**验收**
- 12 演唱调 × 12 指法调换算有单元测试全覆盖；负品数不出现在候选里。
- 指法库覆盖 12 根音 × 14 种性质，每个至少一种按法；缺失项有测试报出。
- 给定一份第 2 步的 `Analysis` + 一组 `Arrangement` 参数，能得到完整的"可渲染结构"（每小节的和弦名、按法、节奏型、页眉）。
- 只改演唱调不改指法调时，输出的和弦名不变（测试）。

---

## 第 4 步：渲染与导出（三层谱）

**做什么**
- SVG 渲染：和弦图、六线谱节奏型行、歌词行（本步用占位文本，第 5 步接真歌词）、页眉、小节线与小节号。
- SVG → PNG（第一页）与多页 PDF。
- MusicXML 导出（music21）：和弦符号 + 六线谱 + 歌词。
- 排版以 `docs/reference/desperado-sheet.webp` 为标准（简谱行留空位，M2 填）。

**验收**
- 用第 3 步的输出渲染出的 PNG，与参考谱并排放在 PR 里，负责人目视确认"像那张谱"。
- 渲染一首 4 分钟歌曲 ≤ 5 秒。
- MusicXML 能被 MuseScore 4 打开，和弦、六线谱、歌词完整，可以直接改单个和弦并重新排版。
- 切换指法调 / 节奏型 / 简化开关后重新渲染，结果正确（截图对比测试）。

---

## 第 5 步：歌词：粘贴对齐 + 识别

**做什么**
- 粘贴对齐：给定歌词文本 + 人声轨，输出行级与音节级时间（英文音节用 pyphen / CMUdict 切分，中文一字一音）。中 / 英各选对齐模型并实测。
- 识别：faster-whisper 在人声轨上出文本，再走同一条对齐。
- 歌词行接入第 4 步渲染。

**验收**
- 准备一个小测试集：中、英各 ≥ 5 首，人工标注行起始时间。
- 粘贴对齐：行级误差 ≤ 0.5 秒的比例 ≥ 90%。
- 识别：给出中、英各自的字错率 / 词错率数字（基线，不设门槛），纯乐器段落不出现幻听文本。
- 无人声的歌曲（纯音乐）能正确返回"无歌词"而不是报错。
- 重新对齐一首歌 ≤ 30 秒。

---

## 第 6 步：Discord Bot（M1 完成）

**做什么**
- 按 `docs/plans/frontend-discord.md`：`/transcribe`、`/status`、`/delete`、`/help`，消息右键入口。
- 谱子消息：PNG 预览 + 嵌入 + 7 个控件；只有发起者能操作。
- 任务队列、GPU worker、配额（每用户每天 5 首）、数据保留（原音频即删、结果 30 天）。
- 中 / 英文案。
- Docker Compose 一键部署 + 自部署文档。

**验收**
- 在一个测试服务器和私信（用户级安装）里完整走通：上传 → 回执 → 出谱 → 换演唱调 / 指法调 / 节奏型 / 简化 / 粘贴歌词 → 导出 PNG / PDF / MusicXML。
- 4 分钟歌曲从上传到出谱 ≤ 5 分钟（含排队为空时）。
- 非发起者点击控件得到提示且无效果。
- 配额、超时、格式错误、超长、无人声各有明确文案。
- 按自部署文档，在一台干净机器上 30 分钟内跑起来。

---

## 第 7 步：人声旋律 → 简谱行（M2 完成）

**做什么**
- 人声轨音高提取（RMVPE / CREPE）→ 切音符 → 量化到拍网格 → `Note`。
- 简谱渲染：音级、八度点、时值（下划线、附点、连音线、休止），接入第 4 步的空位。
- 歌词音节挂到音符（时间最近 + 单调约束）。
- MusicXML 加入旋律声部与歌词音节。

**验收**
- 测试集（第 5 步的 10 首）上，负责人逐首目视 / 试唱确认简谱"大体能跟着唱"，记录明显错误类型。
- 每个歌词音节都挂到且只挂到一个音符，顺序单调。
- MusicXML 在 MuseScore 4 里旋律可播放、歌词在音符下。
- 4 分钟歌曲：旋律环节 ≤ 30 秒。

---

## 第 8 步：公共实例上线

**做什么**
- 租用 GPU 云服务器，部署第 6 步的 Compose。
- 监控：队列长度、各环节耗时、失败率；告警。
- `/help` 里的服务条款、隐私说明；Bot 名称与头像。
- 公共 Bot 安装链接。

**验收**
- 连续 7 天可用，失败率 < 5%。
- 配额与 30 天清理按预期执行（有日志证据）。
- 月成本有数字，与用量对得上。

---

## 每步交给 agent 时的固定要求

- 先读 `CLAUDE.md`、`docs/REQUIREMENTS.md`，再读本步相关的 plan 章节。
- 只做本步范围内的事；需求第 10 节"后续开发"里的东西一律不做。
- 引入任何模型权重前，把许可证写进 `docs/plans/backend.md`。
- 验收标准里的数字必须由脚本产出，并把脚本和结果一起提交。
- PR 描述里逐条对照本步的验收标准打勾。
