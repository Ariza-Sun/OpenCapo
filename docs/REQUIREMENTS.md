# OpenCapo 需求文档（阶段 1）

> 版本：v0.2 草稿。本文档只覆盖**阶段 1**；阶段 1 做不到或不做的功能统一放在第 11 节"后续开发"。
> 标注 **[待定]** 的条目需要拍板，标注 **[建议]** 的是起草人的倾向性意见。

## 1. 背景与目标

市面上的"听歌扒谱"工具（Capo、Lamucal、Chordify、Moises）都是闭源收费产品。国内吉他谱平台的弹唱谱全靠人工编配，覆盖不到的歌就没有谱。

OpenCapo 的目标：

- 用户在 **Discord** 里上传一首歌的音频，几分钟后得到一张**中文吉他弹唱谱**（和弦图 + 六线谱节奏型 + 简谱 + 歌词）。
- 用户可以在 Discord 里用下拉框和按钮调整指法调、节奏型、和弦，粘贴歌词重新对齐，导出 PDF / 图片 / MusicXML。
- 代码开源，任何人可以自部署一个 Bot；我们同时运营一个租用云服务器的公共实例。

明确不做（阶段 1 之外的见第 11 节）：

- 本地运行的桌面 / 命令行软件（已决定不走这条路）。
- 段落结构自动检测（intro / verse / chorus）。
- AI 翻唱 / 换声。
- 向用户提供分轨音频（分轨只作为内部分析的中间产物）。
- 歌曲库、社区分享、账号体系、付费墙。

## 2. 产品形态

### 2.1 形态：Discord 纯 Bot（已定）

阶段 1 只用 Discord 原生组件：斜杠命令、附件、消息、嵌入、按钮、下拉菜单、弹窗（表单）、图片 / 文件附件。**不做** Discord Activity（内嵌网页）和外链网页。

由此接受的限制（已确认）：没有光标跟随音频的同步播放，没有拖拽式编辑，没有波形 / 频谱交互。这些在第 11 节。

### 2.2 安装方式

| 方式 | 说明 | 已定 / 待定 |
|---|---|---|
| 服务器安装 | 服务器管理员把 Bot 加进服务器，成员在频道里用 | 已定 |
| 用户级安装 | 用户把 Bot 装到自己账号下，在私信或任何服务器里用，不需要管理员 | 已定：支持 |

### 2.3 运行环境

| 项 | 说明 |
|---|---|
| 运行位置 | 我们租用的云服务器，**需要 GPU**（CPU 跑一首歌超过十分钟，撞 Discord 的 15 分钟交互令牌上限） |
| 公共实例 | 由我们运营；因此需要排队、限流、用户配额（见第 7 节） |
| 自部署 | 提供 Docker 镜像与部署文档，别人可以用自己的 Discord 应用和服务器跑一份 |

### 2.4 Discord 硬约束及应对

| 约束 | 数值 | 应对 |
|---|---|---|
| 附件大小 | 免费用户每个附件约 10 MB（Discord 改过几次，以当前官方文档为准；服务器加成后更高） | 输入格式实际限于 mp3 / m4a / ogg / opus；4 分钟 128 kbps mp3 约 4 MB。wav / flac 超限时给出明确提示 |
| 交互必须 3 秒内应答 | | 先回"已收到，排队中 / 处理中，预计 N 分钟"，跑完再发后续消息 |
| 交互令牌有效期 | 15 分钟 | 单曲全流程目标 < 5 分钟；超过 15 分钟时改发普通频道消息 / 私信 |
| 下拉菜单 | 每个最多 25 项 | 指法调（12 项以内）、节奏型（控制在 25 以内，或分类两级） |
| 弹窗 | 最多 5 个文本框，每框 4000 字 | 粘贴歌词、改和弦够用 |
| 按钮 | 每条消息最多 25 个（5 行 × 5） | 够 |
| 消息长度 | 2000 字 / 嵌入 6000 字 | 和弦谱文本超长时改为附件 |
| Bot 回传附件 | 同样受上限 | PNG / PDF / MusicXML / MIDI / JSON 均很小，无问题 |

## 5. 阶段 1 功能范围

```
Discord 附件 ──▶ 分析 ──▶ 结构化结果 ──▶ 编配 ──▶ 渲染弹唱谱 ──▶ 发回 Discord
                                                 ▲                      │
                                                 └──── 用户用控件调整 ◀──┘
```

**最终产物（已定）**：一张中文吉他弹唱谱，样式以 `docs/reference/desperado-sheet.webp` 为默认排版标准。从上到下四层：和弦图、六线谱（节奏型 / 指法）、简谱（人声旋律）、歌词（音节级对齐）；页眉含歌名、速度、调号（1=X）、拍号、变调夹提示。

"分析"是**转录**（忠实记录原曲有什么），"编配"是**设计**（根据和弦和节拍生成人能弹的伴奏），两者分开建模。

### 5.1 输入（已定：音频）

| 项 | 要求 |
|---|---|
| 来源 | 斜杠命令的附件参数，或回复 / 引用一条带音频附件的消息 |
| 格式 | mp3 / m4a / ogg / opus（受附件上限约束）；wav / flac 若在上限内也接受 |
| 时长 | **[建议]** 上限 10 分钟；超过提示用户裁剪 |
| 声道 / 采样率 | 任意，内部统一重采样 |
| 歌名 / 艺术家 | 可选参数，用于谱子页眉；未填则用文件名 |

### 5.2 分析输出（数据模型）

所有结果带时间戳（秒），与原音频对齐。

| 对象 | 字段 | 已定内容 |
|---|---|---|
| `Beat` | time, is_downbeat, bar_index, beat_in_bar | 做到小节 + 拍 |
| `Tempo` | bpm（全局） | 只要全局 BPM，不做局部速度曲线 |
| `Key` | tonic, mode(major/minor), 置信度 | 做。简谱的 1=X 和变调夹换算都依赖它 |
| `Chord` | start, end, root, quality, bass（转位）, 置信度 | 见下 |
| `Note`（人声旋律） | start, end, pitch(MIDI), 量化后的时值（起始拍、长度、附点、连音） | 只做人声旋律；必须到音符并量化到拍网格，供简谱渲染 |
| `LyricSyllable` | start, end, text, line_index, note_ref | 中、英；音节级对齐（英文按音节拆 Des-pe-ra-do，中文一字一音），每个音节挂到一个音符 |
| `Stem` | 音频 × {vocals, drums, bass, other} | **内部中间产物**：用于歌词识别（人声轨）、和弦识别（去鼓）、节拍识别（鼓 + 贝斯）、旋律追踪（人声轨）；不存储超过处理周期，不对用户提供 |

**和弦（已定）**：
1. 覆盖面向 Capo 看齐：根音 12 种；性质至少覆盖大、小、7、maj7、min7、6、m6、sus2、sus4、5、dim、aug 等 14 种；**必须支持转位**（如 D/F#、G/B）。
2. 每个和弦带置信度，低置信的在谱上用不同样式标出，提醒复核。
3. 和弦边界对齐到拍网格：先检测节拍，再在拍 / 小节网格上标和弦。

**旋律 + 歌词的预期**：这两项技术上最难（人声滑音 / 颤音切成离散音符有损；音节对到音符两边都可能错）。原则是 **AI 出初稿，人来改**。歌词提供"粘贴歌词文本、系统只做对齐"模式，准确率远高于从零识别，且不受语言限制；不做自动联网抓歌词（版权）。

### 5.3 编配（已定）

| 项 | 规则 |
|---|---|
| 指法调与变调夹 | 用户**只选指法调**（C / G / D / A / E 等好按的调），系统按 `变调夹品数 = 原曲调 − 指法调` 算出夹几品，给出该指法调下的和弦名与和弦图。品数 > 7 的选项排后 / 标灰。保留手动覆盖变调夹与任一和弦 |
| 和弦指法 | 每个和弦给一个默认按法，用户可换 |
| 节奏型 | **可选**：默认按速度 / 拍号推荐一个，用户可从节奏型库换，也可选"无"（六线谱行只显示和弦变化点） |
| 前奏 / 间奏 | **留空**，不做乐器旋律转录 |
| 简谱 | 由人声 `Note` + `Key` 渲染为音级（1–7，高低点）+ 时值记号（下划线、附点、连音线、休止） |
| 简化和弦显示 | 开关：把 Cmaj7 显示为 C、G/B 显示为 G 等，底层数据不变 |

### 5.4 Discord 交互

#### 命令

| 命令 | 参数 | 作用 |
|---|---|---|
| `/transcribe` | `audio`(附件, 必填), `title`, `artist`, `lyrics`(可选文本) | 发起分析；回"排队中 / 处理中 + 预计时间"，完成后发谱子消息 |
| `/status` | | 查看自己排队中 / 处理中的任务 |
| `/help` | | 用法 |

**[建议]** 命令名和所有界面文案提供中 / 英两套，按用户的 Discord 语言设置选。

#### 谱子消息（核心界面）

一条消息，包含：
- 谱子 PNG 预览（第一页；多页时附完整 PDF）
- 嵌入信息：歌名、调（原曲调 / 指法调 / 变调夹）、BPM、拍号、低置信和弦数量提示
- 控件：

| 控件 | 类型 | 行为 |
|---|---|---|
| 指法调 | 下拉 | 每项显示"X 调指法（夹 N 品）"，选后重新出图 |
| 节奏型 | 下拉 | 含"无"；选后重新出图 |
| 简化和弦 | 按钮（开 / 关） | 切换后重新出图 |
| 改和弦 | 按钮 → 弹窗 | 填"小节.拍 = 和弦"，支持一次填多条（每行一条）；支持"全部 X 替换为 Y" |
| 换指法 | 按钮 → 下拉 | 先选和弦，再从该和弦的候选按法里选 |
| 歌词 | 按钮 → 弹窗 | 粘贴 / 修改歌词全文，系统重新对齐、重新出图 |
| 变调夹 | 按钮 → 弹窗 | 手动覆盖品数 |
| 速度 / 拍号 | 按钮 → 弹窗 | 手动改 BPM 标记、拍号 |
| 导出 | 下拉 | PDF / PNG 全页 / MusicXML / MIDI / ChordPro 文本 / 项目 JSON |
| 恢复上一版 | 按钮 | 回退最近一次修改（替代撤销 / 重做，保留最近 N 版） |

- 谁能操作控件：**[建议]** 发起者 + 该频道有"管理消息"权限的人；其他人点击时提示"请先 `/transcribe` 自己的一份"。**[待定]**
- 每次修改都重新渲染并**编辑原消息**（不刷屏）。

#### 任务生命周期

```
收到 → 校验（格式 / 大小 / 时长 / 配额） → 入队 → GPU 处理 → 渲染 → 发消息
                                                      │
                                                  失败 → 告知原因（超时 / 无人声 / 识别失败等）
```

## 6. 差异化（竞品没有的）

已定：
- **中文弹唱谱（简谱 + 六线谱 + 歌词）一键生成**。四家竞品都不出简谱，国内平台靠人工。最大差异点。
- **Discord 原生**：零安装，群里直接出谱、群成员协作纠错。
- **选指法调而不是选变调夹**：用户只选"用哪个调的指法弹"。
- **和弦置信度**：低置信和弦在谱上标出。
- **简化和弦开关**。
- **粘贴歌词对齐模式**。
- **开源 + 可自部署 + 导出全部免费**。

候选（阶段 1 之后）：见第 11 节。

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 硬件 | 云服务器 + GPU（已定：租用）。**[建议]** 起步一张消费级 / 入门数据中心卡即可（如 24 GB 显存级别） |
| 单曲处理时间 | 目标：4 分钟歌曲全流程（分轨 + 节拍 + 和弦 + 调性 + 旋律 + 歌词 + 渲染）**< 5 分钟**，硬上限 15 分钟 |
| 并发与排队 | 单 GPU 串行处理，队列可见；预计等待时间回给用户 |
| 配额 **[待定]** | **[建议]** 每用户每天 N 首（如 5），每服务器每天 M 首；超出提示明日再来或自部署 |
| 数据保留 **[待定]** | **[建议]** 原音频与分轨在处理完成后立即删除；分析结果与谱子保留 30 天供继续编辑，之后删除；用户可随时 `/delete` |
| 隐私 | 不做遥测以外的数据收集；不把用户音频用于训练 |
| 版权 | 不分发音频衍生物（分轨、变速变调音频）；谱子（和弦 + 歌词 + 旋律）与现有和弦谱站同等风险水平。服务条款中注明用户须对上传内容负责 |
| 许可证 **[待定]** | MIT / Apache-2.0 / AGPL。注意：作为托管服务，AGPL 能要求他人修改后也开源；依赖侧 Demucs MIT、WhisperX BSD、madmom BSD，部分模型权重为 CC-BY-NC（需逐个核对商用条款，即使我们不收费也要核对） |
| 多语言 | 界面文案中 / 英；歌词识别中 / 英 |
| 可观测性 | 每个任务各环节耗时、失败原因、队列长度有日志与指标 |
| 可测试性 | 和弦 / 节拍 / 调性准确率在公开数据集上有基准（Isophonics/Beatles、RWC、GTZAN-Rhythm） |

## 8. 架构（初步）**[建议]**

```
Discord ──▶ Bot 网关（接命令、校验、回执、控件事件）
               │
               ▼
          任务队列（Redis / 数据库表）
               │
               ▼
          GPU Worker（分轨 → 节拍 → 和弦 → 调性 → 旋律 → 歌词对齐）
               │
               ▼
          结果存储（结构化 JSON + 版本历史）
               │
               ▼
          编配 + 渲染服务（指法 / 节奏型 / 简谱 → SVG → PNG / PDF / MusicXML）
               │
               ▼
          Bot 发消息 / 编辑消息
```

- 分析 Worker 和渲染服务分开：用户每改一次和弦只走渲染，不重跑模型，秒级返回。
- 核心库（音频 → 结构化结果 → 谱）与 Discord 适配层分离，便于以后接 Activity 或别的前端。

候选开源组件（均有权重、许可证明确）：

| 环节 | 候选 |
|---|---|
| 分轨 | Demucs (HTDemucs)、BS-RoFormer |
| 节拍 / 强拍 | all-in-one (mir-aidj)、Beat This!、madmom |
| 和弦 | BTC、ChordFormer、autochord |
| 调性 | 基于和弦统计的规则法 + essentia key extractor |
| 人声旋律 | RMVPE / CREPE 提取音高 → 自写音符切分与量化 |

| 制谱渲染 | 六线谱 / 和弦图：alphaTab 或 Verovio；简谱：自绘 SVG；MusicXML 生成：music21 |
| Discord | discord.py / discord.js；用户级安装用 Discord 的 User Apps 能力 |

## 10. 验收标准（阶段 1）

- 在 Discord 频道或私信里，上传一首 4 分钟 mp3，5 分钟内收到四层弹唱谱 PNG + PDF。
- 和弦准确率：Isophonics Beatles 数据集 major/minor 级别 ≥ 80%。
- 节拍 F-measure：GTZAN ≥ 85%。
- 切换指法调后，变调夹品数与全部和弦名正确换算（单元测试覆盖 12 × 12 组合）。
- 粘贴正确歌词后，行级对齐误差 ≤ 0.5 秒（抽样人工核对）。
- 改一个和弦 → 重新出图 ≤ 5 秒。
- 导出的 MusicXML 能被 MuseScore 4 打开且和弦、歌词、六线谱完整。
- 任务失败时用户收到可理解的原因，不出现静默失败。

| 拖拽改和弦边界 / 拍点 / 小节线 | 需要图形界面 | Activity |
| 波形 / 频谱图 | 需要图形界面 | Activity |
| 图形化改简谱音符 | 需要图形界面 | Activity |
| 分轨音频下载 / 播放 | 已决定不给用户 | 不计划 |
| 前奏 / 间奏乐器旋律转录 | 多音转录准确率不足 | basic-pitch + 人工修正 |
